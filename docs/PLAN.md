
# 5개 시스템 통합 관리 대시보드 — 구축 작업 리스트 및 실행 계획

## 1. 구축 범위

| 항목 | 내용 |
|---|---|
| 대상 | 미리, 코이 등 5개 운영 시스템 및 해당 EC2/RDS 리소스 |
| 핵심 목표 | 서버·DB 상태 확인, 웹/API 장애 감지, 장애 알림 및 복구 이력 관리 |
| 구축 원칙 | 기존 서비스 변경 최소화, 모니터링과 대시보드 분리, 최소 권한 보안 적용 |

## 2. 단계별 작업 리스트

### 1단계 · 현황 조사 (1~2일)

- [ ] 5개 시스템 목록 작성: 서비스명, 담당자, 운영/개발 환경
- [ ] AWS 계정 ID, 리전, EC2 인스턴스 ID, RDS 식별자 정리
- [ ] 도메인/API URL, 헬스체크 가능 여부, SSL 인증서 만료일 확인
- [ ] 현재 CloudWatch, SNS, 로그 수집 및 알림 설정 확인
- [ ] 장애 심각도와 알림 수신자(개발/운영 담당자) 정의

### 2단계 · 모니터링 기반 구축 (1~2일)

- [ ] 모니터링 서버 또는 기존 관리 서버 재사용 여부 결정
- [ ] Uptime Kuma 설치 및 관리자 접근 제한 설정
- [ ] 5개 시스템의 웹/API HTTP 모니터 등록 (30~60초 간격부터 시작)
- [ ] EC2 CloudWatch Agent 설치 및 메모리/디스크 지표 수집
- [ ] 각 RDS의 CPU, 연결 수, 여유 메모리, 여유 스토리지 지표 확인

### 3단계 · 알람과 알림 채널 (1~2일)

- [ ] CloudWatch Alarm 생성: CPU, 메모리, 디스크, 상태 검사
- [ ] RDS 알람 생성: CPU, 연결 수, 메모리/스토리지 여유
- [ ] SNS 이메일 구독 및 구독 확인 완료
- [ ] Uptime Kuma 장애/복구 알림 채널 설정
- [ ] 중복 알림 방지, 연속 실패 횟수, 복구 알림 정책 설정

### 4단계 · PHP 통합 대시보드 (3~5일)

- [x] 관리자 로그인, 권한 및 VPN/IP 제한 적용
- [ ] 전체 현황 화면: 서비스 상태, 장애 수, 마지막 점검 시각
- [ ] 서비스 상세 화면: 웹/API, EC2, RDS 상태 및 최근 지표
- [x] 장애 센터: 발생/복구 시각, 심각도, 담당자, 조치 내용
- [ ] AWS AssumeRole 또는 안전한 API 연동으로 여러 계정 지표 조회
- [x] CloudWatch/Uptime Kuma 이벤트를 대시보드에 연동 (수신 API, [ALERTS.md](ALERTS.md))
- [ ] 서비스 목록, 리소스, 점검 결과, 장애 이력 DB 테이블 구성

### 5단계 · 검증 및 운영 전환 (1~2일)

- [ ] 테스트 URL/API 장애를 발생시켜 감지 및 알림 확인
- [ ] CloudWatch 임계치 테스트 및 복구 알림 확인
- [ ] 메모리/디스크 지표가 정상적으로 수집되는지 확인
- [ ] 대시보드 자체 장애 시에도 외부 알림이 동작하는지 확인
- [ ] 운영 매뉴얼, 담당자, 장애 대응 절차 및 점검 주기 문서화

## 3. 초기 모니터링 기준 (안)

> 원본 계획서에 표 내용이 비어 있어 일반적인 시작값으로 채운 초안입니다. 1단계 현황 조사 후 확정합니다.

| 대상 | 지표 | 경고 기준(안) | 판정 조건(안) |
|---|---|---|---|
| 웹/API | HTTP 응답 | 2xx/3xx 이외, 타임아웃 | 60초 간격, 연속 3회 실패 |
| 웹/API | 응답 시간 | 2초 이상 | 매 점검 (경고 표시만, 문자 없음) |
| 웹/API | SSL 인증서 | 만료 30일 / 14일 / 7일 전 | 일 1회 |
| EC2 | CPUUtilization | 80% 이상 | 5분 평균, 3회 연속 |
| EC2 | 메모리 사용률 (Agent) | 85% 이상 | 5분 평균, 3회 연속 |
| EC2 | 디스크 사용률 (Agent) | 80% 이상 | 5분 평균, 1회 |
| EC2 | StatusCheckFailed | 1 이상 | 1분, 2회 연속 |
| RDS | CPUUtilization | 80% 이상 | 5분 평균, 3회 연속 |
| RDS | DatabaseConnections | max_connections의 80% 이상 | 5분 평균, 2회 연속 |
| RDS | FreeableMemory | 전체의 10% 미만 | 5분 평균, 3회 연속 |
| RDS | FreeStorageSpace | 전체의 20% 미만 | 5분 평균, 1회 |

## 4. 권장 기술 구성 (안)

> 원본 계획서에 표 내용이 비어 있어 초안으로 작성했습니다.

| 영역 | 구성 | 비고 |
|---|---|---|
| 외부 감시 (웹/API/SSL) | Uptime Kuma (Docker) | 대시보드와 분리 운영, 독립 알림 |
| 서버/DB 지표 | CloudWatch + CloudWatch Agent | 메모리·디스크는 Agent 필요 |
| 알람/알림 | CloudWatch Alarm → SNS (이메일) | 대시보드 중단과 무관하게 동작 |
| 대시보드 | PHP 8.x + Composer (이 저장소) | Nginx + PHP-FPM |
| 대시보드 DB | MySQL/MariaDB | 서비스·리소스·점검 결과·장애 이력 |
| AWS 연동 | AWS SDK for PHP + STS AssumeRole | 계정별 읽기 전용 Role (최소 권한) |
| 이벤트 연동 | Uptime Kuma Webhook, SNS → HTTPS 구독 | 장애/복구 이벤트를 대시보드에 적재 |
| 접근 제어 | 관리자 로그인 + VPN/IP 제한 | 보안 그룹 및 웹서버 레벨 이중 적용 |

## 5. 예상 일정 및 비용

- **일정**: 약 7~13 작업일 (계정 권한, 기존 설정, 테스트 범위에 따라 변동)
- **운영비 예산**: 월 $10~50 추가 비용을 초기 검토 범위로 설정하되, 실제 CloudWatch 지표·로그·알람/API 사용량과 서버 재사용 여부로 산정
- **비용 확인**: 서울 리전 기준 AWS 요금표 및 실제 사용량으로 검증. 위 범위는 견적이 아닌 초기 예산 가이드.

## 6. 완료 기준 (검수 체크리스트)

- [ ] 5개 시스템이 대시보드에 등록되어 상태를 확인할 수 있다.
- [ ] 웹/API 장애가 정해진 횟수 내 감지되고 장애 및 복구 알림이 전달된다.
- [ ] EC2 CPU·메모리·디스크와 RDS 핵심 지표가 조회된다.
- [ ] 장애 발생·복구 이력과 조치 내용이 저장된다.
- [ ] 중앙 대시보드가 중단되어도 CloudWatch/Uptime Kuma의 독립 알림이 유지된다.
- [ ] 관리자 접근이 제한되고 AWS 권한이 최소 권한으로 구성되어 있다.
